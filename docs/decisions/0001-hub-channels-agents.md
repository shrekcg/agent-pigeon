# 0001 分成渠道、中枢、Agent 三层

- 状态：已采纳（2026-10-29）

## 背景

v1 只做了一件事：飞书话题和 PenguinHarness 会话一一对应，所有逻辑都写在一个 1500 行的 `relay.js` 里。新需求是：

- 下面要接多个 Agent，它们的协议各不相同（HTTP+SSE、各家命令行的 JSON 流、Unix socket）；
- 上面以后还要接钉钉、QQ、微信，而且这些平台有的有话题，有的没有；
- 有时要每个会话一个话题，有时要所有会话进同一个对话。

## 决策

参考 Magpie（上接 Agent、下接模型的网关）的分层思路，但信鸽不是网关，它只做绑定和转发：

- **渠道**负责平台上的事：收消息，打开一个位置（话题或名片），把运行事件渲染成平台上的内容（卡片、文字），并且自己决定一条消息属于哪个绑定。
- **Agent 适配器**负责会话上的事：列出会话、发送消息、停止、审批，把原生协议翻译成统一的运行事件。
- **中枢**只管绑定和路由，不知道某个具体平台或 Agent 的细节。

## 后果

- 加一个 Agent 或一个渠道，各自只需要写一个目录，再登记一行。
- 隔离方式成了渠道自己的事：话题模式和共享模式的区别只体现在 `open` 和 `resolveBinding` 两个方法里。
- 代价是多了一层间接：运行事件必须是 Agent 和渠道的最小公约数，Agent 特有的能力只能通过 `capabilities` 暴露出来。
